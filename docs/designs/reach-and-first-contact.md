# Design: phase 3 — reach, not more evidence

Generated by /office-hours on 2026-08-28

## Problem Statement

Phases 1 and 2 were built on a premise recorded in `docs/designs/experiment-layer.md`:
that this repository is limited by how its evidence is presented rather than by what
it contains. Phase 2 shipped five commits of presentation and evidence — two shift
experiments, a regression check, a data integrity manifest, an interactive replay, an
inference contract, a generated model card.

The premise is now tested, and it did not hold. The repository has been shared and
produced no observable signal: no questions, no follow-up, no mention. More rigor is
not the lever.

## Demand Evidence

Weak, and honestly reported. The strongest available evidence of anyone reading this
is "shared, no signal back" — links in applications and a profile, nothing returned.

Two facts, verified during the session rather than assumed, explain part of the
silence without implying anything about the quality of the work:

- `reports/report.html` is gitignored. The link to it
  added at README.md:242 during the replay commit **404s on GitHub for every reader.**
  The ten-second replay — the only artifact here that lands in seconds rather than
  minutes — is unreachable to anyone who does not clone the repo and run a 35-minute
  pipeline.
- The GitHub repository has no description and no homepage URL. The first thing any
  visitor sees is blank.

The claude.ai artifact link at README.md:17 may or may not resolve for a logged-out
stranger. Unverified, and worth two minutes to check.

## Status Quo

The reader is a hiring manager or screener reaching this through a job application.
Their current behaviour: roughly thirty seconds on a CV, and a repository link that is
usually never opened at all. The competitor is not another candidate's project. It is
nothing — the link going unclicked.

That channel also returns no information either way, which is why two phases of work
produced no feedback signal to learn from.

## Target User & Narrowest Wedge

**User:** a technical screener or hiring manager who opens the repository page and
decides within a minute whether to keep reading.

**Wedge:** one URL that opens the replay in a browser, with no clone, no build, and no
account. Everything else in the repository is depth for a reader who has already
decided to stay; this is the artifact that earns that decision.

## Constraints

- `scripts/build_html_report.py` reads only committed inputs — `reports/REPORT.md`,
  `reports/figures/`, `reports/replay.json`. **CI can rebuild the full HTML report
  without the 310 MB dataset.** Publishing costs a workflow file, not a data pipeline.
- `reports/report.html` is gitignored deliberately: 774 KB of inlined base64 that
  rewrites itself on every run. Committing it would add churn to every diff. The fix
  must publish it without tracking it.
- There is no `.github/` directory: no CI exists yet in this repository.
- No amount of code changes the click-through rate of a link in an application form.

## Premises

Agreed during the session:

1. The constraint is arrival, not craft.
2. The best artifact is currently unreachable.
3. The status quo competitor is nothing — the default outcome is that the link is
   never clicked.
4. The evidence is finished. Nothing in `TODOS.md` would change the mind of a reader
   who has not read what already exists.
5. No artifact fixes a channel with no clicks. Part of phase 3 is action the author
   takes, not code.

## Approaches Considered

### Approach A: make it reachable

Summary: GitHub Pages workflow builds and deploys the HTML report on push; fix the
404'd README link to point at the published URL; add a repository description, homepage
URL, and a social preview image so a shared link renders as a card.
Effort: S (human: ~2h / CC: ~30 min). Risk: Low.
Reuses: `scripts/build_html_report.py` and `make html` unchanged.
Pros: removes a verified defect; small and finishable; prerequisite for everything else.
Cons: does nothing about arrival — most likely outcome is the same silence with a
working link.

### Approach B: publish the finding, not the repository

Summary: one standalone piece aimed outward, built from a finding that stands on its
own — the two-boundary transfer result (discrimination survives a boundary the
operating point does not), or the ordering-only result (97% of full AUROC from features
containing no measured value). The repository becomes the appendix rather than the
pitch.
Effort: M (human: ~1 day / CC: ~1h). Risk: Medium — a public post can flop.
Pros: attacks arrival directly; returns real feedback, which the application channel
never does; the findings are genuinely interesting to strangers.
Cons: a flop is real information, and not the enjoyable kind.

### Approach C: aim it at named people

Summary: a one-screen entry tailored to five to ten named humans, sent directly with a
specific ask.
Effort: S in code, unbounded in nerve. Risk: low technically.
Ruled out for now as the phase's centre of gravity, not on merit — it is the
highest-conversion option, and it survives below as The Assignment.

## Recommended Approach

**A, then B.** A alone repeats the phase-2 mistake of polishing without a reader. A is
a prerequisite for B: there is no point driving anyone to a 404.

Sequence:

1. `.github/workflows/pages.yml` — build `report.html` from committed inputs, deploy to
   GitHub Pages. No dataset required.
2. Fix README.md:242 to point at the published URL. Audit every other link in the
   README the same way; one was already wrong.
3. Repository description, homepage URL, social preview.
4. Verify the claude.ai artifact link at README.md:17 in a logged-out browser, and
   replace it with the Pages URL if it does not resolve.
5. Then the write-up: one piece, one finding, aimed at a stranger.

## Open Questions

- Does the claude.ai artifact link at README.md:17 resolve for a logged-out reader?
  Two minutes to check, and it changes whether step 4 is a fix or a formality.
- Which finding carries the write-up: the two-boundary transfer result, or the
  ordering-only 97%? The second is more surprising; the first is more useful.
- Where does the write-up go? A post has a distribution problem of its own, and this
  design does not solve it.

## Success Criteria

Measurable, in order of what they prove:

1. The replay opens from a public URL in a logged-out browser in one click, no clone
   and no build. Binary, checkable today.
2. Zero broken links in the README, verified rather than assumed.
3. The repository page shows a description and a working homepage link.
4. **At least one piece of unsolicited feedback from a stranger who read it.** This is
   the only criterion that tests the premise. The first three are hygiene.

## Distribution Plan

GitHub Pages, deployed by GitHub Actions on push to `main`. The workflow runs
`python scripts/build_html_report.py` against committed inputs and publishes
`reports/report.html` as the site root. `report.html` stays gitignored — it is built in
CI, never tracked, which keeps the 774 KB of base64 out of every diff.

## Dependencies

- GitHub Pages enabled on the repository (a settings change, done once, by the author).
- `reports/REPORT.md`, `reports/figures/` and `reports/replay.json` must stay committed;
  the workflow depends on them. `make clean` removes them, so a clean-then-push would
  break the build. Worth a note in the workflow.

## The Assignment

Two things, both this week, neither of them code.

**First, two minutes:** open the claude.ai link at README.md:17 in a private browser
window, logged out. If it does not load, you have found a second broken front door and
the silence needs no further explanation.

**Then, the real one:** send the repository to one person you know who screens
candidates or reviews technical work. Not a group, not a post — one named person. Ask
them for sixty seconds and one question: *"What do you think this project is about?"*

Their answer is the only unbiased read you can get of whether the first ninety seconds
work. If they describe the leakage measurement or the transfer finding, the artifact
converts and the problem is purely reach. If they describe "a sepsis model," the first
screen is not doing its job, and no amount of depth below it will help.

## What I noticed about how you think

- You picked "shared, no signal back" when three more flattering options were sitting
  right next to it. Most people take the one that implies the work landed. Choosing the
  honest option about your own project is the same instinct that produced
  `DECISIONS.md` and the model card's limitations section.
- Your instruction all session was some version of "commit this", "merge to main and
  push". Never "let me think about it". The shipping cadence is real and it is not
  common.
- You asked "what do we do next?" rather than naming the next thing. That is how you
  get good recommendations, and it is also how a project ends up with five phases of
  excellent work and no reader. The one question nobody asked for four phases was
  "who is this for?"
- You chose A-then-B over A-alone, which means accepting a public post that might get
  no response. That is the correct call and it is the uncomfortable one.
